# 月套餐与学期套餐设计

## 背景与目标

当前生产收费系统已经支持微信 Native 一次性支付，并已上线 `CREDIT_PACK_100`（990 分 CNY、100 credits）。本次扩展在不引入自动续费或委托扣款的前提下，上线月套餐和学期套餐，并复用现有订单快照、支付查询、原子结算、权益、额度、退款和对账体系。

本次新增的可售订阅商品为：

- `PRO_MONTHLY`：名称 `Pro Monthly`，1990 分 CNY，有效期 30 天，权益版本 `pro-v1`。
- `PRO_SEMESTER`：名称 `Pro Semester`，7900 分 CNY，有效期 150 天，权益版本 `pro-semester-v1`。

`CREDIT_PACK_100` 保持 990 分 CNY、100 credits，不改变既有行为。

## 范围

本次包含商品目录、服务端激活门禁、订单创建门禁、订阅结算、用户界面、退款兼容、测试和分阶段上线。

本次不包含自动续费、自动扣款、套餐升级或降级、有效期叠加、按月重置学期额度、支付宝、微信 JSAPI、小程序或 H5 支付。

## 商品与权益规则

月套餐有效期为付款结算后的 30 天，使用现有 `pro-v1` 周期额度。学期套餐有效期为付款结算后的 150 天，使用 `pro-semester-v1` 周期额度；每个功能的额度为对应月套餐额度的五倍。学期额度在完整 150 天周期内共享，不按月重置。

两种订阅均为一次性付款，创建的订阅必须保持 `auto_renew=false`。价格、币种、有效期、套餐 ID 和权益版本均来自服务端持久化商品及不可变订单快照，客户端不能提交或覆盖这些字段。

## 有效订阅门禁

用户存在尚未到期的 `ACTIVE` 订阅时，不得创建任何新的订阅商品订单，包括从月套餐切换到学期套餐或反向切换。服务端必须在创建订单前查询当前订阅，并以 `409 ACTIVE_SUBSCRIPTION_EXISTS` 拒绝请求；拒绝路径不得创建订单、占用支付意图或调用微信接口。

前端同步禁用月套餐和学期套餐入口，显示当前套餐与到期时间，但前端仅用于解释状态，不作为安全边界。有效订阅用户仍可购买 `CREDIT_PACK_100`。

订阅到期后可正常购买任一订阅套餐。首版不提供提前续购、排队生效、套餐升级、差价补缴或剩余权益折算。

## 支付与结算

两种订阅复用现有微信 Native 支付链路：读取活动商品、创建服务端订单快照、创建支付意图和二维码、查询或接收已验证的微信结果，然后调用现有原子结算 RPC。

成功结算必须在一个数据库事务中完成：

1. 将订单和支付记录推进到已支付终态。
2. 创建恰好一条以订单为来源的 subscription。
3. 按订单中的不可变权益快照创建 entitlement。
4. 为每个非空周期额度创建 subscription 关联的 usage quota，周期起止时间与 subscription 完全一致。

重复支付查询、重复微信通知或并发结算必须返回已有结果，不得重复创建 subscription、entitlement 或 quota。数据库唯一约束和结算 RPC 的终态检查继续作为双重幂等保护。

## 数据库与后台安全门禁

新增版本化 Supabase 迁移，以幂等方式校验并更新两个套餐及其权益记录，并扩展后台允许激活的 SKU 白名单。迁移必须验证：

- `PRO_MONTHLY` 只能是 1990 分 CNY、30 天、`pro-v1` 的订阅商品。
- `PRO_SEMESTER` 只能是 7900 分 CNY、150 天、`pro-semester-v1` 的订阅商品。
- 学期套餐的 13 项周期额度严格等于月套餐对应额度的五倍。
- `CREDIT_PACK_100` 的现有定义保持不变。
- `PRO_YEARLY`、`FREE` 和其他 SKU 仍不能通过管理接口激活。

生产迁移与应用部署必须分离审批。不得通过直接修改生产行来绕过迁移历史或服务端安全门禁。

## 用户界面

套餐页展示月套餐、学期套餐和 100 credits 包三张商品卡。订阅卡明确显示价格、有效期、主要额度和“不自动续费”；学期套餐说明额度覆盖整个 150 天且不按月重置。

支付确认页继续展示服务端商品快照，并要求用户同意会员服务和退款规则。订单详情显示套餐名称、支付状态、订阅起止时间、额度使用情况与退款入口。

有效订阅用户访问套餐页时，两个订阅按钮均禁用，并显示当前套餐到期时间；credits 包入口保持可用。若客户端状态过期或接口被直接调用，服务端返回相同的 409 门禁错误。

## 退款规则

月套餐与学期套餐统一使用现有订阅退款规则。完全未使用的订阅可提交并执行全额原路退款，退款结算同时撤销订阅、权益和未使用 quota。只要任一相关额度已经使用，系统不得自动退款，只能进入人工审核。

退款操作必须保持既有审计、幂等和微信退款安全约束；本次不新增按比例退款或剩余天数折算。

## 错误处理与安全

配置错误、数据库不可用、微信响应异常和结算失败继续映射为既有安全错误响应。日志只记录允许的事件码、服务端订单标识和固定状态，不得记录支付密钥、私钥、API v3 Key、完整证书、Authorization、原始回调或二维码内容。

公开支付开关继续作为独立生产门禁。开发和部署过程不得修改 staging，不得提交真实支付配置，也不得在未经单独确认时执行生产迁移或部署。

## 测试与验收

实现遵循测试驱动流程，先添加会失败的测试，再进行最小实现。测试至少覆盖：

- 两种套餐的 SKU、价格、币种、有效期、权益版本和订单快照。
- 月套餐各项额度及学期套餐严格五倍关系。
- 有效订阅期间拒绝创建月套餐或学期套餐订单，且不调用支付 Provider。
- 有效订阅期间仍允许购买 `CREDIT_PACK_100`。
- 到期订阅不阻止新订阅订单。
- 微信支付成功后只创建一次 subscription、entitlement 和 quotas。
- 重复查询、重复通知和并发结算不重复发放权益。
- 未使用订阅可全额退款，已有使用只能进入人工审核。
- UI 正确展示三种商品、订阅期限、不自动续费和已有订阅门禁。
- 日志和 API 响应不泄露敏感支付信息。

提交前运行定向测试、全量测试、类型检查、Lint、生产 Build 和 `git diff --check`。

## 上线策略

上线分为代码准备、生产迁移、候选部署、白名单实付和公开开放五个独立检查点。每个生产变更都必须获得明确确认，并保留可验证的回滚路径。

候选版本先在独立端口启动 canary，验证健康、商品目录与配置门禁。生产迁移完成并登记历史后才允许切换应用。白名单分别完成月套餐与学期套餐的受控实付验收，核验订单状态、订阅期限、额度和幂等性；验收成功后再单独批准普通用户公开销售。
