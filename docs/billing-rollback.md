# 收费 MVP 回滚手册

## 适用原则

回滚以停止新增风险并保留完整账务为目标。不得删除订单、支付、订阅、权益、额度流水、回调事件、退款/发票申请或管理员审计数据，也不得用历史 migration 的反向删除脚本处理生产问题。

## 应用层紧急停止

1. 将服务端 `BILLING_FEATURE_ENABLED=false` 并重新启动应用实例。
2. 确认公开购买入口消失，订单、支付、Mock 确认、退款和发票写接口拒绝请求。
3. 停止创建新订单；不要把已有订单或支付记录批量改为成功、失败或删除。
4. 若真实 Provider 曾启用，在商户平台暂停产品或支付能力，同时保留只读查询、对账和人工处置渠道。
5. 保留支付回调审计；如必须阻断入口，应在受控边界返回明确失败，并记录变更时间，避免伪造成功响应。

## 应用代码回滚

- 回滚到上一个已验证的应用版本，不修改备案底栏、域名、部署工作流、Nginx、DNS 或 SSL 配置。
- 先保持 `BILLING_FEATURE_ENABLED=false`，验证认证、既有科研功能及账务只读能力。
- 不得通过回滚代码让旧版本写入它不理解的新账务状态；必要时保持 Billing 写接口关闭。
- 未经明确确认，不推送 `main`、不触发生产部署。

## 数据库处置

- 数据库迁移采用向前修复：新增修复 migration、约束或兼容 RPC，不改写已执行的历史 migration。
- 不得删除账务数据，不得回退已经产生订单、支付或额度流水的表结构。
- 在独立测试数据库重现问题并验证修复后，经过备份、评审和明确授权才可进入生产变更流程。
- 若数据库写入异常，先关闭功能并停止新订单，保留账务历史和原始回调审计，再进行人工对账。
- 对处理中订单、退款和回调事件建立清单，逐条核对 Provider 记录与本地账务；禁止脚本式批量猜测状态。

## 恢复开放检查

只有以下条件全部满足后才考虑重新开放：

- 根因和影响范围已确认；
- 修复有自动化回归测试，并在独立 PostgreSQL 环境验证；
- 订单、支付、退款、订阅和额度完成对账；
- Provider 回调签名、金额、币种与幂等重放验证通过；
- 安全、业务、法务及备案相关负责人明确批准；
- 先对白名单测试账号灰度，再决定是否开放普通用户。

默认保持：

```dotenv
BILLING_FEATURE_ENABLED=false
PAYMENT_MODE=mock
```
